How to Write Review Notes

Notes can be added at 3 levels. Use the prefixes below to keep them actionable and traceable.

Level 1: Requirement Notes (REQ-XXX)

Big-picture feedback on the requirement's scope, clarity, or completeness.

APPROVED Requirement is clear, scoped, and matches the product intent.

SCOPE GAP Capability X is also required but not mentioned here. Add it.

UNCLEAR "Validates input" is vague. Should list the specific rules.

WRONG Description contradicts the product brief — verify with stakeholder.

MISSING REQ No requirement covers feature Y. Add a new REQ.

Level 2: User Story Notes (US-XXX)

Feedback on whether the story captures the right user intent and workflow step.

OK Story accurately describes the workflow.

WRONG PERSONA "As a developer" should be "As an end user".

SPLIT This story covers two distinct flows — split into two stories.

MISSING STORY No story for the delete/undo path.

DUPLICATE Same functionality as US-XXX. Remove one.

Level 3: Acceptance Criteria Notes (AC-XXX)

Precise feedback on individual Given/When/Then criteria — the most important level for implementation correctness.

VERIFIED Matches the expected behaviour.

INCOMPLETE "Shows error" doesn't specify the message. Add the exact text.

MISSING AC No AC for: "Given X, when Y, then Z."

WRONG BEHAVIOR AC says 3 seconds, should be 5 seconds.

UNTESTABLE "Performs well" is not measurable — rewrite with a numeric threshold.

ADD AC Missing happy-path AC.

Quick Status Decision Guide

Approved = Requirement/story/ACs are correct and ready.
Needs Changes = Mostly correct but has gaps, unclear wording, or missing ACs.
Rejected = Fundamentally wrong, duplicate, or out of scope.

How Auto-Save Works

This HTML and its JSON sibling live in the same directory. A local dev server handles both reading and writing:

Data flow:
Browser → PUT request → dev server → writes JSON to disk

On page load: GETs the JSON, loads into memory.
On every change: Updates memory → debounced 1s → PUT writes to disk.

If a teammate pushed updated reviews: git pull then refresh the page.

Getting Started

1. Make sure both files are in the same directory: <feature>-requirements-review.html and <feature>-requirements-review.json.
2. Serve the directory with a PUT-capable dev server. Any of:
    - The project's existing dev harness (if it accepts PUT on JSON files)
    - A simple Node/Python middleware that forwards PUT to fs.writeFile
3. Open this HTML in the browser. Header shows green Auto-saving when ready.
4. If the banner "Enable auto-save" appears, click Connect once.
5. If PUT is unsupported, all edits still persist to localStorage; use Export Copy to share a snapshot.

Saving & Sharing

Auto-save to disk: Every change writes to the JSON file within 1 second.

Commit when ready:
git add <feature>-requirements-review.json && git commit -m "Review: ..."
Export Copy (header button) downloads a timestamped JSON snapshot for sharing via Slack/email. It does NOT modify the project file.

Review Workflow

1. Walk through each section (themes/pages) in order.
2. For each requirement: expand it, read the description, expand the stories and ACs.
3. Compare each AC against the expected behaviour or the product brief.
4. Set status (Approved / Needs Changes / Rejected) and add notes at the appropriate level.
5. Every change auto-saves to disk — no manual save needed.
6. When done, git commit the JSON and push.
